# 這個專案是怎麼做出來的

[English](story.md)

我是 Head of Products，不是職業工程師。Product Mission Control 一開始是我替自己做的工具，用來處理
自己的產品組合工作。這個 repo 是那個私人專案經過修訂、整理後的公開版本，目的是讓別人看得到它怎麼
運作，也看得到它是怎麼做出來的。

## 為什麼要做

我的工作是把產品方向、成果、交付承諾、決策、風險，以及支撐這些判斷的證據串在一起。實際上這些
資訊散在任務工具、文件、儀表板和會議紀錄裡；畫面很快就過時，寫狀態報告又吃掉原本該拿來做決策的
時間。

我想要一個本機的工作空間，對產品組合做的事，就像 X 光片對醫生做的事：告訴你該看哪裡、哪些事
最需要注意、為什麼。但它不下診斷。每一個重要變更都要經過一份精確的預覽，由我核准或拒絕；每一個
結論要嘛有 Evidence 支撐，要嘛是我親手寫下、自己負責的 Judgment。

由此定下三條原則：

- 系統負責揭露與排序，人負責決定。沒有任何事會替我核准。
- 沒有事情會悄悄消失。拒絕會被記錄；還沒決定就關掉審閱單，不會被記錄。
- 永遠留一條退路。規則再嚴也不能讓工作卡死：只驗證了一部分的 Evidence，寫下 Judgment 就能往前；
  從未驗證的 Evidence 則不行。

## 先打地基，再寫程式

我沒有從寫程式開始。第一週產出的是專案地基，用的是我之前公開的 agent skill
[Project Kickoff Foundation](https://github.com/kevintu2007/project-kickoff-foundation)：產品目的、
隱私邊界、領域語言、架構分層、錯誤處理、驗證指令與審查流程，每一項都標明已確認、提議中或待決。

接著是設計，分成幾道關卡：概念、附互動原型的設計簡報，以及一份 UI 契約。這份契約在 2026 年 8 月
17 日寫下第一行應用程式碼之前就凍結了。

## 我怎麼帶 AI agent 工作

我負責方向與決策，程式大部分由 AI agent 撰寫。完整做法寫在
[Working with AI agents](working-with-ai-agents.md)（英文），重點如下：

- **Claude Code** 是 orchestrator：一次規劃並實作一小片，先寫測試。
- **Codex** 是獨立的審查者：一般變更用標準模型審查，架構與機制設計交給更強的模型評估。寫的人永遠
  不能核准自己的成果。
- 本地模型處理範圍明確、低風險的工作。
- 只有我能做決定：每個目標由我設定，每個會改變規則的問題由我回答，每個使用者看得到的切片，我都
  要看過真實 app 的截圖才接受。

讓這一切保持誠實的規則很短：地基凍結、只能填充；測試連續失敗兩次就停下來交還給我；agent 不自己
開 issue、不自行擴大範圍；任何東西都不能因為「結構看起來完整」就宣稱完成。

## 審查關卡抓到了什麼

審查不是走形式。以下幾個發現，都在往下做之前修好了：

- **8 月 13 日，設計審查：** 原型裡正在撰寫的報告，畫面重新渲染時會遺失尚未儲存的文字。
- **8 月 27 日，整合審查：** 重新解決 Issue 時會附上過期的 Evidence，重放的稽核事件帶錯 correlation
  id。修好之後，把修正還原，新測試會再次失敗，證明這個修正確實是關鍵。
- **8 月 31 日，里程碑結案前的審查：** 重放一個已核准的變更時，讀的是紀錄「現在」的樣子，而不是
  「核准當下」的樣子，導致之後再編輯就無法重啟。後續稽核在九類紀錄中的七類找到同樣的缺口，全部修正。
- **9 月 5 日，受管投影的稽核：** 一個已核准的雜湊從來沒有被拿去比對，另外有一個「已同步」狀態，
  沒有任何上線的程式碼能到達。這次稽核為專案留下最重要的一條規則：不能因為某個需求的「形狀」存在
  就宣稱已滿足，要確認真的有程式碼產生它、也有程式碼強制它。修法是重新推導預期結果，整體比對。
- **9 月 17 日，準備這個公開 repo：** 拍攝教學截圖時，發現一個畫面在寫入後還顯示舊數字；匯出審查
  則發現程式註解裡到處是內部任務編號。兩者都在公開前修好。

## 難題

上面的審查發現是正確性問題。下面這些是要花設計功夫的：每一個都先由審查者評估，再由我書面決定，
然後才動手做。

- **重放「核准當下」，不是「現在」（8/31–9/2）。** 核准一個準備好的變更時，必須重新推導整份快照，
  和預覽當成一個整體比對。最早的實作重放的是紀錄現在的樣子；稽核在九類紀錄裡的七類找到這個缺口。
  修法後來變成一條規則，之後每個機制都照著做。
- **解釋得出來的排序（9 月）。** Work Queue 用六個具名層級，再看最早的期限，再看類型與識別碼。
  沒有加權分數，所以每個位置都能用一句話說明；新增一種注意原因時，沒給它層級就無法編譯。
  書面版本是[注意力排序](../policies/attention-ranking.md)政策（英文）。
- **驗證快了三倍（9/19）。** 每次寫入交易都先從全部 46 個 migration 重建正典 schema，再和實際的
  schema 比對。改成每個程序只算一次，並在測試設定裡用最佳化編譯的 SQLite，四個代表性的測試執行檔
  從 914 秒降到 294 秒；完整的 `npm run verify` 從約 155 分鐘變成 36 到 46 分鐘。先量測，再決定。
- **歷史不隨 Evidence 失效（9/19）。** Issue 已執行的歷史是用 Evidence「現在」的驗證狀態重建的，
  所以 Evidence 事後失去驗證，整個 Issue 快照就載入失敗。現在改讀準備該轉移時就存下的
  prepared-intent 快照；兩個測試在舊的解碼器上會失敗。
- **重啟也不會重複建立（9/22）。** 建立紀錄時，先用表單的請求 id 在獨立交易裡持久地保留識別碼，
  所以另一次啟動的重試會指向同一筆紀錄，不會多出第二筆。「已保留」的證明是一個型別，Ledger crate
  以外的程式碼造不出來。
- **備份閘門（9/22）。** 在自己的工作區，加密備份驗證通過之前不接受一般寫入，而且閘門要在整個交易
  期間持有。第一版設計把自己的測試鎖死；「連續失敗兩次就停」的規則中止了它、交回給我。和審查者
  一起重新設計後，拆成一把准入鎖和一把短暫的狀態鎖，每次備份拿一張會自行釋放的票。
- **不用 `unsafe` 的還原（9/22）。** 在 Windows 上安全地換掉使用中的 SQLite 檔案，設計成兩段式改名，
  每個階段都寫進控制紀錄；啟動時把當機打斷的事做完或退回，絕不打開換到一半的 Ledger。審查四輪：
  第一輪八個發現，之後還有一個不是 compare-and-set 的退回階段，以及一條可能打開半換檔案的啟動路徑。
- **就地升級（9/22）。** 較舊的 Ledger 先唯讀檢查、以關閉的檔案備份並驗證，再在一個交易裡升級：
  `BEGIN` 前關掉外鍵，commit 前做外鍵檢查。審查找到一個可偽造的備份證明和一張可重放的收據，兩者
  都在做畫面之前補上。
- **路徑不跨越邊界（9/21–9/23）。** 選擇檔案與資料夾的視窗由主機開啟；介面只拿到一個不透明、會過期
  的 token 和用來顯示的名稱。路徑包含檢查拒絕連結與 reparse point；整個程式碼裡唯一一處 `unsafe`，
  是用 Windows 自己的方式比較路徑名稱。還沒解的也寫下來：一段只有 Windows API 才能關上的
  time-of-check 空窗，列為已知限制，而不是藏起來。

## 從私人工具到這個 repo

私人專案保留完整的歷史、agent 指示與審查紀錄。這個 repo 由它單向匯出：只放白名單內的產品檔案，
文件依照現在的程式碼重寫，再由掃描擋下任何帶有私人路徑、地址或內部參照的檔案。公開前也把程式註解
改寫過，讓每一則註解用文字說明它的需求，而不是指向某個內部任務。

它是 beta：第一個附安裝程式、加密備份與還原、可以存放真正紀錄的版本。設計裡的檢視期間、Fact Pack、
核准後的報告快照都還沒做，app 裡也還沒有接任何 AI 助理。[README](../../README.zh-TW.md) 清楚列出今天能用的部分。
